    Ferramentas externas: consultas e ações¶

    O painel permite cadastrar até três ferramentas externas por assistente em Integrações → Consultas a sistemas (API). Cada uma é de um de dois tipos:

    • Consulta (GET): só lê. O assistente consulta durante a conversa e usa o resultado na resposta.
    • Ação (POST): faz algo no seu sistema (agendar, abrir chamado, registrar lead). O assistente só propõe; a ação roda depois que o cliente toca em Confirmar. Veja Ações com confirmação do cliente.

    O ciclo é opcional: sem ferramenta ativa, a mensagem usa o fluxo normal de inferência.

    Limites da primeira versão¶

    • Só aceita endpoint HTTPS público na porta padrão; endereços locais, IPs literais, DNS que resolve para rede privada, redirects, credenciais na URL e query strings fixas são bloqueados.
    • Consulta é GET e não altera nada. Ação é POST e sempre pede confirmação do cliente; não há PUT, PATCH nem DELETE.
    • Cada ferramenta declara no máximo oito argumentos (string, integer, number ou boolean): na consulta, codificados como parâmetros de query; na ação, como corpo JSON. O modelo só preenche os de origem modelo; os demais o servidor preenche (veja abaixo).
    • Cada mensagem executa no máximo uma ferramenta; o ciclo faz uma chamada ao modelo para escolher a ferramenta e outra para redigir a resposta. A função exige o adaptador Groq.
    • A resposta externa tem limite de 64 KB na conexão e é reduzida a 8.000 caracteres antes de ser enviada ao modelo. A auditoria registra ferramenta, canal, status, latência e erro curto por até 90 dias; não persiste argumentos, resposta ou segredo.
    • Credenciais são cifradas com TARS_ENCRYPTION_KEY, nunca retornadas à interface. O cabeçalho permitido é X-API-Key ou Authorization.

    Configuração de argumentos¶

    Informe o endpoint sem query string. Exemplo para uma API de pedidos:

    https://api.exemplo.com/v1/pedidos

    No painel, cada parâmetro é uma linha com nome, tipo, descrição e Quem preenche. Pela API, a mesma configuração fica assim:

    [
  { "nome": "sku", "descricao": "Código exato do produto", "tipo": "string", "obrigatorio": true, "origem": "modelo" },
  { "nome": "loja_id", "descricao": "Loja", "tipo": "string", "obrigatorio": false, "origem": "fixo", "valor": "loja-42" },
  { "nome": "pedido", "descricao": "Pedido do cliente", "tipo": "string", "obrigatorio": false, "origem": "coleta", "campo": "pedido" }
]

    O TARS valida nomes e tipos de novo antes de chamar a API. Os valores são acrescentados com URLSearchParams; não mudam host, método ou cabeçalhos.

    Quem preenche cada parâmetro¶

    Origem No painel Quem decide o valor
    modelo (padrão) O assistente, pela conversa O modelo, a partir do que o cliente escreveu.
    fixo Valor fixo O operador: valor com até 500 caracteres, em uma linha, compatível com o tipo.
    coleta Campo coletado A conversa: a chave (campo) de um dos campos obrigatórios das Regras de atendimento.
    • Configurações antigas sem origem continuam valendo como modelo; não há migração.
    • Parâmetros fixo e coleta não podem ser marcados como obrigatórios: o servidor os preenche sempre. A descrição continua obrigatória e serve só para o painel.
    • O modelo não vê parâmetros fixo nem coleta na definição da ferramenta. Se mesmo assim mandar um deles, a chamada é recusada ("A ferramenta recebeu parâmetros não autorizados.").
    • Uma ferramenta com parâmetro coleta só entra na lista daquela mensagem quando a coleta da conversa terminou e tem o campo. Antes disso (ou se o campo não existe naquele canal), ela fica de fora sem erro para o cliente, e o log registra [tars] ferramenta <nome> sem campo coletado <campo>.
    • No painel, cada campo da lista mostra em que canais as Regras o pedem (todos, Telegram ou Site: a lista própria de um canal substitui a geral). Se o campo escolhido não é pedido num canal em que o assistente atende, um aviso diz que lá a ferramenta não fica disponível.
    • O campo precisa existir nas Regras de atendimento ao salvar: se ele foi removido, o servidor recusa ("O campo coletado “x” não existe mais nas Regras de atendimento…") e, ao editar, o painel limpa a escolha.
    • O playground não tem conversa: consulta com campo coletado não roda lá, e o painel avisa.
    • O valor coletado é o que o cliente respondeu na coleta. Ele amarra a consulta ao que aquela conversa informou, não a uma identidade verificada.

    Ações com confirmação do cliente¶

    Uma ação é uma ferramenta do tipo Ação (POST). O modelo nunca a executa: ele só propõe. O servidor grava uma ação pendente, mostra ao cliente um resumo e os botões Confirmar e Cancelar, e só chama o seu sistema quando o toque chega pelo canal.

    Como cadastrar¶

    No formulário, escolha Tipo → Ação (POST), preencha endereço, autenticação e parâmetros como numa consulta e escreva o Texto de confirmação. Pela API, a configuração leva "metodo": "POST" e "resumo_template":

    {
  "nome": "agendar", "descricao": "Agenda uma visita na loja",
  "endpoint": "https://api.exemplo.com/v1/agendamentos", "metodo": "POST",
  "resumo_template": "Agendar sua visita para {data} na loja {loja}?",
  "parametros": [
    { "nome": "data", "descricao": "Dia da visita", "tipo": "string", "obrigatorio": true, "origem": "modelo" },
    { "nome": "loja", "descricao": "Loja", "tipo": "string", "obrigatorio": false, "origem": "fixo", "valor": "loja-centro" }
  ]
}

    Configurações sem metodo continuam sendo consultas GET.

    O texto de confirmação¶

    • Obrigatório na ação, até 300 caracteres.
    • {nome} é trocado pelo valor do parâmetro com esse nome (do modelo, fixo ou coletado). Só valem nomes de parâmetros da própria ação; chave solta ou nome desconhecido é recusado no cadastro.
    • Parâmetro sem valor aparece como "—". Valor com mais de 200 caracteres é cortado com "…", e o resumo inteiro tem no máximo 3.500 (o Telegram corta mensagens em 4.096). O corte vale só para o texto que o cliente lê; o POST leva os valores inteiros.
    • O texto é seu, não do modelo: o cliente confirma exatamente o que o template diz, com os valores que serão enviados.
    • Os valores que o modelo escolheu passam pela mesma conferência de saída das respostas: link de fora, citação inventada ou o código secreto do prompt bloqueiam a proposta (o cliente não vê botão e o atendimento vai para a equipe). Link que você escreveu no próprio template sai normalmente.

    O que o cliente vê¶

    Agendar sua visita para amanhã na loja loja-centro?
Toque em Confirmar para eu fazer isso, ou em Cancelar.
[Confirmar] [Cancelar]

    No Telegram os botões são um teclado da mensagem (callback_data acao:<id>:ok ou acao:<id>:nao); no Webchat, botões no widget. Depois do toque, a resposta é fixa e também não passa pelo modelo:

    Situação Resposta
    O seu sistema respondeu 2xx Pronto! (o resumo)
    Erro, timeout ou resposta fora de 2xx Não consegui concluir. Tente de novo ou fale com a equipe.
    O cliente tocou em Cancelar Tudo bem, não fiz nada.
    Passaram 10 minutos, ou o pedido não é desta conversa Esse pedido de confirmação expirou. Se ainda quiser, me peça de novo.
    Dois toques quase juntos (a primeira chamada ainda em curso) Já estou fazendo isso. Aguarde um instante.
    A execução ficou sem resposta (a função caiu no meio) e a validade passou Não consegui concluir. Tente de novo ou fale com a equipe.
    Toque vindo de um grupo do Telegram Ações só funcionam em conversa privada.
    O atendimento está com uma pessoa da equipe (bot pausado) Seu atendimento está com uma pessoa da equipe; a ação não foi executada.

    Regras¶

    • Sempre confirma. Não existe ação "sem confirmação" nem nível de risco: toda ação POST passa pelo toque do cliente.
    • 10 minutos. A proposta vale 10 minutos; depois, o toque não executa. Não há tarefa agendada: a validade é conferida no próprio toque. Ao tocar, a validade passa a contar da execução (2 minutos), para uma confirmação no fim da janela não ser dada como falha no meio da chamada.
    • Atendimento humano. Se a conversa foi para a equipe depois da proposta, o toque não executa: a ação fecha como cancelada (erro atendimento humano, "Não executada" no painel).
    • Uma pendente por conversa. Uma proposta nova cancela a anterior da mesma conversa.
    • Uma execução só. O toque muda a ação de pendente para executando numa única operação no banco; segundo toque, reenvio do Telegram ou botão copiado para outra conversa não executam de novo.
    • Idempotency-Key. O POST leva o cabeçalho Idempotency-Key: <id da ação>. Se o seu sistema guardar a chave, um eventual reenvio também não duplica do lado dele.
    • Corpo e limites. O corpo é o JSON dos argumentos (do modelo, fixos e coletados), até 32 KB; o teto da chamada é de 10 segundos. Mesmo destino seguro da consulta: HTTPS público, sem redirect, credencial cifrada no cabeçalho escolhido.
    • Só em conversa privada no Telegram. Num grupo qualquer membro poderia tocar em Confirmar; lá a ação nem é oferecida ao modelo, e um toque vindo de grupo é recusado sem executar. No Webchat cada sessão é de uma pessoa.
    • Execução sem resposta. Se a função cair entre o início da chamada e o resultado, a ação fica "em andamento" até a validade de 2 minutos da execução passar; depois disso o painel mostra "Falhou" (erro "sem resposta da função") e o cliente que tocar de novo lê "Não consegui concluir…". O seu sistema pode ter recebido o POST: confira pela Idempotency-Key.
    • Fora do playground. O playground não tem botão para o cliente confirmar: a ação nem é oferecida ao modelo lá, e a tela avisa.
    • Webhooks. Ao terminar, sai o evento acao.executada (2xx) ou acao.falhou para os webhooks que o assinam, com ferramenta, resumo e status_http, nunca os argumentos. A execução que ficou sem resposta (acima) não gera evento.
    • Painel. O cartão Ações recentes mostra as 20 últimas propostas (ação, resumo, status e quando); o histórico de execuções registra a chamada como "nome (ação)", sem argumentos nem resposta.

    Por que sempre confirma¶

    O modelo lê texto do cliente e da base de conhecimento, e esse texto pode conter instruções escondidas. Se o modelo também pudesse executar uma escrita, uma injeção de prompt viraria uma ação real (OWASP LLM06, agência excessiva). Aqui a execução depende de um sinal que texto nenhum produz: o toque no botão, que chega pelo canal (callback_query no Telegram, botao no Webchat) e é conferido contra a instância, o canal e a conversa da proposta. Pela "regra de dois" (um agente não deve, ao mesmo tempo, ler entrada não confiável, acessar dado sensível e mudar estado sem um humano no meio), a ação fica segura por construção: quem muda o estado é o cliente, ao confirmar o resumo que o operador escreveu.

    Fluxo de execução¶

    Telegram/Webchat
  → regras, autorização do canal e cotas
  → ferramentas com campo coletado só entram se a coleta da conversa terminou
  → modelo escolhe uma ferramenta e emite os argumentos de origem modelo
  → validação desses argumentos; servidor acrescenta fixos e coletados
  → consulta: requisição HTTPS GET com timeout, limites e sem redirect
      → resposta truncada e marcada como dado externo não confiável
      → modelo formula a resposta final
  → ação: grava a pendente e responde o resumo do template com Confirmar/Cancelar
      → toque do cliente pelo canal → POST com Idempotency-Key → frase fixa
  → trilha operacional sem conteúdo sensível

    O TARS não adiciona uma assinatura por habilitar a função, mas não consegue verificar o plano, saldo, cotas ou cobrança vinculados à chave Groq nem ao serviço consultado. O ciclo pode fazer uma inferência adicional e a API externa pode cobrar. Verifique as contas e limites antes de ativar; não há garantia de custo zero por parte do TARS. A resposta do endpoint é enviada ao Groq para gerar a resposta e deve ser adequada para processamento pelo modelo.

    API administrativa¶

    GET /api/ferramentas?instancia_id=... lista configurações sem segredos (com metodo e resumo_template). POST /api/ferramentas cria ou atualiza uma configuração e DELETE /api/ferramentas remove; todas exigem sessão e permissão de edição na instância. GET /api/ferramentas/execucoes?instancia_id=... lista o histórico resumido. GET /api/ferramentas/acoes?instancia_id=... lista as 20 últimas ações propostas (permissão de leitura).

    As tabelas ferramentas_api, ferramentas_api_execucoes e acoes_pendentes têm RLS habilitada e privilégios revogados para os papéis anon e authenticated; a aplicação valida a permissão da equipe antes de ler ou alterar os dados.

    Fora de escopo por enquanto¶

    • PUT, PATCH e DELETE. Ação é só POST.
    • Retentativa automática: a ação que falha não é repetida; o cliente pode pedir de novo, e o Idempotency-Key muda a cada proposta.
    • Saber se o destino recebeu uma ação que ficou sem resposta: o TARS marca como falha, mas o POST pode ter chegado. Um pedido novo gera outra Idempotency-Key.
