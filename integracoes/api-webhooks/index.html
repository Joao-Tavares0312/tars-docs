    API e webhooks¶

    Duas formas de ligar o TARS a outro sistema seu (planilha, CRM, painel interno) sem depender da Zendesk:

    • API REST: o seu sistema lê conversas, atendimentos e contatos de um assistente, com uma chave própria. Só leitura.
    • Webhooks: o TARS avisa o seu sistema, na hora, a cada evento que você marcar (mensagem recebida, atendimento aberto…), com um POST assinado.

    As duas ficam no painel em Integrações › API e webhooks (/painel/configuracoes/api) e exigem permissão de edição no assistente (titular, admin ou editor). Criar, revogar e remover entram na auditoria do assistente, sem o token nem o segredo; do endereço do webhook, a auditoria e o alerta de desligamento guardam só origem e caminho (sem a query, que às vezes leva um token do seu sistema).

    Chaves de API¶

    1. Abra Integrações › API e webhooks, escolha o assistente e clique em Nova chave.
    2. Dê um nome (por exemplo, o sistema que vai usá-la) e clique em Criar chave.
    3. Copie o token que aparece (tars_ + 43 caracteres). Ele não é mostrado de novo: o banco guarda só o sha256 dele e os 12 primeiros caracteres (tars_ + 7), que aparecem na lista para você reconhecer a chave.

    Cada assistente pode ter até 5 chaves ativas. Revogar (com confirmação) corta o acesso na hora: o próximo pedido com aquela chave recebe 401.

    A chave é o escopo: ela só enxerga o assistente onde foi criada, nunca outro da mesma conta.

    Autenticação e limites¶

    Todo pedido leva o cabeçalho:

    Authorization: Bearer tars_...
    Situação Resposta
    Sem chave, chave em formato errado, inexistente ou revogada 401 {"erro": "..."}
    Mais de 120 pedidos por minuto com a mesma chave 429 {"erro": "..."}
    Mais de 30 recusas por chave inválida no último minuto, do mesmo IP 429 {"erro": "..."} (até a janela esvaziar, mesmo com chave válida)
    Parâmetro inválido (ex.: status=xyz) 400 {"erro": "..."}
    Erro inesperado do nosso lado (tente de novo depois) 500 {"erro": "Erro interno."}

    As respostas são sempre JSON, com Cache-Control: no-store. CORS fechado: a API é para servidor falar com servidor; não use a chave no navegador. Os freios (120/min por chave, 30 recusas/min por IP) são por instância de função (em memória), então o teto real pode ser um pouco maior sob carga — não conte com eles como cota.

    ultimo_uso_em da chave é atualizado no máximo uma vez por minuto e aparece no painel como "último uso".

    Paginação¶

    As listas devolvem até limite itens (padrão 50, máximo 100) e um campo proximo. Quando proximo não é null, há mais: repita o pedido com antes=<proximo>. O cursor é opaco — não monte nem edite à mão.

    Endpoints¶

    Todos são GET. Nos exemplos, $TARS é o endereço do seu TARS (ex.: https://seu-tars.vercel.app) e $CHAVE é o token.

    GET /api/v1/eu — confere a chave.

    curl -s "$TARS/api/v1/eu" -H "Authorization: Bearer $CHAVE"

    { "instancia": { "id": "inst_ab12cd34", "nome": "Loja Aurora" }, "chave": { "nome": "Planilha", "prefixo": "tars_Xy3kP9q" } }

    GET /api/v1/conversas?canal=&q=&limite=50&antes= — conversas, da atividade mais recente para a mais antiga. canal é telegram ou webchat; q busca no texto, no chat e no nome/e-mail do contato.

    curl -s "$TARS/api/v1/conversas?canal=webchat&limite=20" -H "Authorization: Bearer $CHAVE"

    {
  "conversas": [
    { "canal": "webchat", "chat_id": "visitante-91", "contato_nome": "Ana", "mensagens": 6,
      "iniciada_em": "2026-10-08T12:00:00.000Z", "ultima_atividade": "2026-10-08T12:04:10.000Z",
      "ultima_mensagem": "Obrigada!", "teve_equipe": true, "teve_falha": false }
  ],
  "proximo": "WzEyMzRd"
}

    GET /api/v1/conversas/{canal}/{chat_id}?limite=50&antes= — mensagens de uma conversa, em ordem de conversa. A página traz as mais recentes; proximo anda para o passado. autor é cliente, bot ou equipe (com agente_nome).

    curl -s "$TARS/api/v1/conversas/webchat/visitante-91" -H "Authorization: Bearer $CHAVE"

    GET /api/v1/atendimentos?status=&limite=50&antes= — tickets, do mais novo para o mais antigo. status: aberto, em_atendimento, resolvido ou fechado.

    curl -s "$TARS/api/v1/atendimentos?status=aberto" -H "Authorization: Bearer $CHAVE"

    GET /api/v1/contatos?q=&limite=50&antes= — contatos com as identidades de canal, do mais novo para o mais antigo.

    curl -s "$TARS/api/v1/contatos?q=ana" -H "Authorization: Bearer $CHAVE"

    Webhooks¶

    1. Em Integrações › API e webhooks, no cartão Webhooks, informe o endereço (https://, porta padrão, sem IP direto e sem usuário/senha na URL).
    2. Marque os eventos e clique em Cadastrar webhook.
    3. Copie o segredo de assinatura (whsec_...). Ele aparece uma vez; o TARS o guarda cifrado só para assinar os envios.

    Até 5 webhooks por assistente. Enviar teste manda um evento teste.ping na hora e mostra a resposta. A lista mostra as últimas entregas (evento, status HTTP, tempo, quando); o TARS guarda as 50 últimas de cada webhook.

    Eventos¶

    Evento Quando dados
    mensagem.recebida o cliente escreveu (Telegram ou site) texto, autor: "cliente"
    mensagem.respondida o bot ou alguém da equipe respondeu texto, autor: "bot" ou "equipe"
    atendimento.aberto a conversa foi para a fila da equipe ticket: {id, status, prioridade}
    atendimento.resolvido o ticket passou para resolvido ticket: {id, status, prioridade}
    csat.respondido o cliente deu a nota da pesquisa nota (1 a 5), ticket: {id}
    acao.executada o cliente confirmou uma ação e o seu sistema respondeu 2xx ferramenta, resumo, status_http
    acao.falhou o cliente confirmou uma ação e o destino respondeu fora de 2xx, deu timeout ou erro de rede ferramenta, resumo, status_http (null sem resposta)
    teste.ping botão "Enviar teste" mensagem

    O corpo é sempre o mesmo envelope:

    {
  "id": "evt_6f1c0e1a-2b7d-4c8e-9a51-3f0d2e7b9c11",
  "evento": "mensagem.recebida",
  "ocorrido_em": "2026-10-08T12:00:00.000Z",
  "instancia_id": "inst_ab12cd34",
  "canal": "webchat",
  "chat_id": "visitante-91",
  "dados": { "texto": "Olá, quero saber do meu pedido", "autor": "cliente" }
}

    texto vem cortado em 2.000 caracteres; nas ações, resumo é o texto de confirmação já preenchido (até 500 caracteres) e os argumentos enviados ao seu sistema não vão no webhook. O webhook nunca leva o prompt do assistente, trechos da base, credenciais nem o e-mail de quem opera o painel: dados passa por uma lista branca no servidor.

    Cabeçalhos de cada POST:

    Cabeçalho Valor
    Content-Type application/json
    User-Agent TARS-Webhook/1
    X-TARS-Evento o nome do evento
    X-TARS-Entrega o id do evento (use para ignorar repetidos)
    X-TARS-Assinatura t=<unix>,v1=<hex>

    Verificar a assinatura¶

    v1 é o HMAC-SHA256, em hex, de "<t>.<corpo bruto>" com o segredo do webhook. Confira sobre os bytes recebidos (antes de qualquer JSON.parse), compare em tempo constante e recuse se t estiver a mais de 5 minutos do seu relógio.

    Node:

    import { createHmac, timingSafeEqual } from "node:crypto";

export function assinaturaValida(segredo, cabecalho, corpoBruto, toleranciaSeg = 300) {
  const campos = Object.fromEntries(String(cabecalho).split(",").map((p) => p.split("=")));
  const t = Number(campos.t);
  if (!campos.v1 || !Number.isFinite(t) || Math.abs(Date.now() / 1000 - t) > toleranciaSeg) return false;
  const esperado = createHmac("sha256", segredo).update(`${campos.t}.${corpoBruto}`).digest();
  const recebido = Buffer.from(campos.v1, "hex");
  return recebido.length === esperado.length && timingSafeEqual(recebido, esperado);
}

//   const evento = JSON.parse(req.body); ... res.sendStatus(200);
// });

    Python:

    import hashlib, hmac, time

def assinatura_valida(segredo: str, cabecalho: str, corpo_bruto: bytes, tolerancia_seg: int = 300) -> bool:
    campos = dict(p.split("=", 1) for p in cabecalho.split(",") if "=" in p)
    try:
        t = int(campos["t"])
    except (KeyError, ValueError):
        return False
    if abs(time.time() - t) > tolerancia_seg or "v1" not in campos:
        return False
    esperado = hmac.new(segredo.encode(), f"{t}.".encode() + corpo_bruto, hashlib.sha256).hexdigest()
    return hmac.compare_digest(esperado, campos["v1"])

    A implementação de referência (a mesma que o TARS usa e que a suíte E2E usa para conferir) está em lib/webhooks/assinatura.mjs.

    Entrega, falhas e limites¶

    • Tempo: cada POST tem 5 segundos. Responda 2xx rápido e processe depois; qualquer outro status, redirect ou erro de rede conta como falha.
    • Sem retentativa. No plano gratuito da Vercel não há fila para tentar de novo mais tarde. Se o seu sistema ficou fora do ar, os eventos daquele intervalo se perdem; use a API REST para buscar o que faltou.
    • 10 falhas seguidas desligam o webhook (etiqueta "desligado após falhas") e abrem um alerta em Operação, enviado também ao seu Telegram se configurado. Para religar, conserte o destino e use Enviar teste: uma entrega bem-sucedida zera o contador e reativa.
    • Destino: só HTTPS público. O endereço é resolvido a cada envio e recusado se apontar para rede privada; redirect não é seguido.
    • Webhook novo: num assistente sem webhook ativo, o TARS lembra isso por até 60 segundos para não consultar o banco a cada mensagem. Cadastrar, remover, desligar ou religar esquece na hora, mas sob carga outra instância da função pode levar até 60 s para começar a enviar.
    • Ordem: os eventos saem depois da resposta ao cliente e podem chegar fora de ordem. Use ocorrido_em para ordenar e id para descartar repetidos.
