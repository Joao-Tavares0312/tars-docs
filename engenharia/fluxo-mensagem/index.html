    Fluxo de uma mensagem¶

    Diagrama¶

    sequenceDiagram
  participant C as Canal/visitante
  participant R as Rota Next.js
  participant DB as PostgreSQL
  participant I as Adaptador de inferência
  C->>R: envia texto (e segredo/origem)
  R->>DB: carrega instância, integração, regras e histórico
  R->>R: valida cota, bloqueio, horário, handoff e coleta
  R->>DB: busca trechos publicados relevantes
  R->>I: prompt + memória + fontes + parâmetros
  I-->>R: resposta, provedor, modelo e latência
  R->>C: entrega resposta
  R->>DB: registra turno e telemetria

    As etapas de validação de segurança antecedem a inferência. Quando há handoff, o bot é pausado e não chama o provedor. Falha de inferência cria alerta e pode abrir ticket humano. Cotas próprias da instância são distintas das cotas do provedor.

    Orquestração e fallback¶

    lib/inferencia/provedor.ts mantém adaptadores prontos. Por padrão, chama somente o primeiro provedor disponível (ou o escolhido pela instância); falhas não enviam os dados a uma segunda conta. O fallback para provedores seguintes exige TARS_ENABLE_PROVIDER_FALLBACK=true, é limitado a falhas recuperáveis e pode mudar destino, privacidade e custo. Falhas de requisição inválida não são mascaradas por tentativas redundantes.

    const candidatos = fila(p.provedor, process.env.TARS_ENABLE_PROVIDER_FALLBACK === "true");
for (const adapter of candidatos) {
  try {
    return await adapter.responder({ ...p, modelo });
  } catch (erro) {
    if (erro instanceof FalhaProvedor && !erro.vaiAdiantarTentarOutro) break;
  }
}

    Exemplo reduzido do orquestrador. O fallback altera o destino do conteúdo: confirme que cada provedor de reserva atende aos requisitos de privacidade antes de configurá-lo.

    Persistência do turno¶

    No sucesso, pergunta e resposta ficam associadas à instância/canal/chat. A telemetria separada guarda provedor, modelo, latência, estimativa de uso, fallback e estado de sucesso. Há deduplicação do update_id recebido do Telegram para impedir que uma nova entrega do mesmo update gere uma resposta duplicada.

    O que não acontece em background¶

    O serviço não mantém uma sonda de saúde sempre ligada. A telemetria vem do tráfego observado e há diagnóstico manual do webhook Telegram. Em plataformas serverless gratuitas, não é seguro prometer um worker agendado contínuo sem outro serviço.
