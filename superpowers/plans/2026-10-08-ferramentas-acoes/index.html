    Task 1 — Ações POST com confirmação do cliente¶

    Objetivo. Hoje as ferramentas externas são só GET. O operador passa a poder cadastrar uma ação (POST): agendar, abrir chamado, registrar lead. O modelo nunca executa a ação: ele só a propõe; o servidor grava uma ação pendente, mostra ao cliente um resumo montado por template (não pelo modelo) com os botões Confirmar e Cancelar, e só executa quando o clique chega pelo canal (callback_data no Telegram, botao no Webchat), um sinal que texto injetado não consegue falsificar (OWASP LLM06). Execução única e idempotente.

    Decisões já tomadas (não reabrir): - Toda ação POST pede confirmação, sempre. Não existe "sem confirmação" nem campo risco: regra simples, sem exceção. A "Rule of Two" do relatório fica satisfeita por construção; documente isso. - O resumo é template do operador com {parametro}; nunca passa pelo modelo. - A resposta depois de executar também é fixa: "Pronto! " / "Não consegui concluir. Tente de novo ou fale com a equipe." / "Tudo bem, não fiz nada." / "Esse pedido de confirmação expirou. Se ainda quiser, me peça de novo." Sem segunda chamada ao modelo. - Uma ação pendente por conversa: nova proposta cancela a anterior. - Ações não rodam no playground (sem botão para confirmar): ferramenta POST fica fora da lista lá, com Aviso na tela, como já acontece com campo coletado.

    Como. 1. Schema (lib/db/schema.sql + garantirSchemaAplicacao em lib/db/cliente.ts): - ferramentas_api: ALTER TABLE … ADD COLUMN IF NOT EXISTS metodo TEXT NOT NULL DEFAULT 'GET' (CHECK em ('GET','POST')) e resumo_template TEXT. - acoes_pendentes(id TEXT PK, instancia_id FK CASCADE, ferramenta_id FK CASCADE, canal TEXT, chat_id TEXT, argumentos JSONB NOT NULL, resumo TEXT NOT NULL, status TEXT NOT NULL DEFAULT 'pendente' CHECK IN ('pendente','executando','executada','falhou','cancelada','expirada'), status_http INTEGER, erro TEXT, criado_em, expira_em TIMESTAMPTZ NOT NULL, concluida_em TIMESTAMPTZ) + índice (instancia_id, canal, chat_id, status) + RLS + REVOKE. Ao inserir, apagar linhas com mais de 30 dias da mesma instância (mesmo padrão de poda de webhook_entregas). 2. Config (lib/ferramentas/config.ts, lib/db/ferramentas.ts, app/api/ferramentas/route.ts): metodo (GET | POST, default GET) e resumo_template (obrigatório quando POST; ≤ 300 chars; só placeholders {nome} de parâmetros existentes; validado por validarTemplate(template, parametros) puro). Nas leituras, linhas antigas sem metodo valem GET. 3. Puro em lib/ferramentas/confirmacao.mjs + tests/ferramentas-confirmacao.test.mjs: validarTemplate, preencherTemplate(template, argumentos) (placeholder sem valor vira "—"), botoesAcao(id) → [[{texto:"Confirmar",dado:"acao:<id>:ok"},{texto:"Cancelar",dado:"acao:<id>:nao"}]], lerBotaoAcao(dado) → {acaoId, confirmar} | null (formato estrito, id ^[A-Za-z0-9_-]{1,64}$), e as quatro frases fixas (fraseAcao(estado, resumo)). 4. Proposta (lib/ferramentas/executar.ts): quando a chamada do modelo é de ferramenta POST, em vez de chamarApiSegura: validar/montar os argumentos como hoje (fixos e coletados incluídos), criarAcaoPendente (lib/ferramentas/acoes.ts: cancela a pendente anterior da conversa, insere com expira_em = now() + 10 min, id = novoId("acao")), e devolver uma RespostaInferencia com texto = resumo preenchido + " Confirma?" (ou o template já em forma de pergunta; decida e documente) e botoes = botoesAcao(id). RespostaInferencia (lib/inferencia/tipos.ts) ganha botoes?: Botao[][] opcional. Sem chatId (playground) a ferramenta POST nem entra na lista (disponiveis). 5. Canais: - Telegram (app/api/telegram/[instanciaId]/route.ts): resposta com botoes sai por enviarComBotoes (ver como /start e o CSAT fazem); callback_query com lerBotaoAcao(data) → confirmarAcao/cancelarAcao e responde o texto fixo (e answerCallbackQuery como o CSAT faz). - Webchat (app/api/webchat/[instanciaId]/route.ts): o JSON da resposta leva botoes quando houver; o POST com b.botao que casa lerBotaoAcao → mesmo fluxo, devolve {texto}. Widget (app/api/webchat/widget/route.ts): quando a resposta do envio traz botoes, renderiza a mesma linha de botões usada nas mensagens da equipe ([data-acoes], post({botao: dado}), desabilita após o clique e mostra d.texto). - Registrar a mensagem do bot com os botões (botoes na tabela mensagens, como enviarAoCanal já faz) para o histórico e o painel. 6. Execução (lib/ferramentas/acoes.ts): confirmarAcao(instanciaId, canal, chatId, acaoId) faz UPDATE acoes_pendentes SET status='executando' WHERE id=… AND instancia_id=… AND canal=… AND chat_id=… AND status='pendente' AND expira_em > now() RETURNING *; sem linha → devolve o estado real (expirada, executada, cancelada ou inexistente) para a frase certa. Com linha: chamarApiSegura({ metodo: "POST", confirmada: true, corpo: argumentos, cabecalhos: credencial, cabecalhosDoServidor: { "Idempotency-Key": acaoId }, timeoutMs: 10_000 }), grava status/status_http/erro/concluida_em, chama registrarExecucaoFerramenta (campo novo metodo opcional na linha ou só no nome; sem gravar argumentos nem resposta, como hoje). cancelarAcao idem com status='cancelada'. Expiração: a própria condição expira_em > now(); sem cron. 7. Modo de teste: como os webhooks (lib/webhooks/entregar.ts: destinoLocalDeTeste + modoTeste()), aceitar endpoint http://127.0.0.1 para ferramentas quando modoTeste() — na validação do cadastro e na chamada (fetch simples com redirect: "manual"). Nunca fora do modo de teste. 8. Provedor falso (lib/inferencia/teste.ts): se ainda não gera chamadasFerramenta, adicionar um gatilho determinístico: mensagem do usuário começando com /usar <nome> <json> e ferramentas presentes → devolve uma chamada daquela ferramenta com aqueles argumentos. Só no provedor falso. 9. Painel (AbaConsultas em components/telas/Integracoes.tsx): campo "Tipo" (Consulta GET / Ação POST, com ajuda: "Ação pede confirmação do cliente antes de executar"), e, quando Ação, campo "Texto de confirmação" com ajuda mostrando os placeholders disponíveis ({data}, …). Lista: etiqueta "ação" / "consulta". Cartão "Ações recentes" (últimas 20 da instância: ferramenta, resumo, status como etiqueta com palavra, quando), via GET /api/ferramentas/acoes?instancia_id= com podeAcessarInstancia(…,"ler"). Aviso no playground quando há ferramenta POST ativa. 10. Docs: docs/integracoes/ferramentas.md (seção "Ações com confirmação do cliente": como cadastrar, o template, o que o cliente vê, Idempotency-Key, 10 minutos, uma pendente por conversa, por que sempre confirma), docs/produto/seguranca.md (LLM06), docs/engenharia/apis-e-dados.md (tabela nova), ROADMAP.md (implementado; remover a pendência "somente leitura"). 11. Testes: - tests/ferramentas-confirmacao.test.mjs (puro) e teste estático provando que executar.ts nunca chama chamarApiSegura com POST fora de acoes.ts, e que acoes.ts usa status='pendente' no UPDATE e manda Idempotency-Key. - E2E tests/e2e/acoes.spec.mjs: servidor falso ganha POST /acao-destino (guarda corpo + cabeçalhos) e GET /acoes-recebidas. Fluxo Webchat: cadastra ação agendar (parâmetro data do modelo + loja fixo, template "Agendar para {data} na loja {loja}?") → /usar agendar {"data":"amanhã"} → resposta com o resumo e dois botões, nada chegou ao falso → clica Confirmar → falso recebeu um POST com {data:"amanhã", loja:…} e Idempotency-Key → texto "Pronto! …" → clica de novo → frase de já concluída/expirada; segundo pedido + Cancelar → nada no falso. Fluxo Telegram: mesmo com cliqueTelegram. Expiração: ajustar expira_em para o passado via tests/e2e/banco.mjs e clicar → "expirou", nada no falso. Também: ferramenta POST não aparece no playground (aviso na tela). - A aba/tela nova de ações entra em responsivo.spec.mjs se for rota ou aba própria (é um cartão na aba existente: só garantir que a rota já coberta continua sem rolagem).
